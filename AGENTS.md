# Active AirV2X project rules

Read `active_view_v0/docs/SCENE_WORKFLOW.md` and the scene's approved brief before changing code or YAML. This file is committed so future sessions can recover the shared process; a new conversation should identify the repository and branch.

1. Translate every scene request into the structured brief in `active_view_v0/docs/scene_brief.template.yaml`: map and junction IDs, coordinate convention, ego spawn and full maneuvers, each sensing agent, traffic groups with direction/speeds/start spacing, signal phases with absolute times, weather, sensor/ROI, clip length, and measurable checkpoints. When the user supplies a sketch, tie pixels to junction IDs and CARLA world coordinates. Show the understood contract and mark material uncertainties before implementing; do not repeatedly ask about decisions already made.
2. Preserve an already working scene as an immutable baseline. One approved geometry/traffic scenario has one complete versioned `configs/<scene_id>.yaml`. Never silently change traffic lights, Ego maneuvers, ROI, GT inclusion, clock, or sensor names. A changed scenario gets a new scene ID/YAML; change `regional_scenario.py` only if the existing engine cannot express the brief.
3. Weather YAML under `configs/weather/` changes **only** `carla.weather`; profiles under `configs/profiles/` change only output or rendering options. Materialize a frozen effective YAML with `python -m active_view_v0.scene_recipe`; use that exact YAML in the editor, preview and/or collector. Keep fixed `carla.seed` when changing weather. Collector writes `effective_config.yaml` into the dataset; keep the source scene, weather and profile file hashes in its `recipe` metadata.
4. Interactivity and offline data are separate: `regional_editor` previews and writes an editor draft, `regional_preview` checks timeline, `regional_collector` writes synchronized sensors, and `regional_pipeline` additionally runs proxy evaluation. A 25-candidate LiDAR dataset is offline counterfactual data, not evidence of a deployed online UAV policy. For real-time experiments, require a causal policy with no access to future frames or GT.
5. Before a 10 Hz long collection, confirm a 0/10/20/30 s preview, sensor/vehicle spawn counts, Ego route and motion, lane legality, signal states, target counts and occlusion, ROI, and drone movement. Test at least one full clip's health and Where2comm model forward; compare center hover plus pre-registered fixed/tracking/patrol baselines and report both AP and recall. Compare policies on the same route, seed, weather and initial UAV position. Never tune or choose a best fixed candidate on test GT and claim it is deployable.
6. Keep all approved source YAML, briefs, code and lightweight test assets in GitHub; keep giant datasets, videos, editor drafts and generated YAML out of Git. Push to a branch based on the latest approved scene; don't overwrite the user's unsynced work. Record the commit hash and source config in each run report.

CARLA's current two-junction generator supports lane-connected straight pairs. A UI selection of a map, junction or clicked point does **not** establish that an arbitrary-turn, three-junction, or previously untested map scene can be simulated; implement and validate a new generator before promising it.
